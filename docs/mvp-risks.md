# MVP 风险评估

> 评估时间：2026-09-02。按「是否会改变项目范围」排序，不按技术难度排序。

## 一、致命级：会改变项目范围

### R1. Wayland 上「贴图」基本无法实现 —— Linux 必须降级

这是整个项目最大的意外，**它直接推翻了「三平台一等公民」的目标**。

Wayland 的安全模型**从协议层面禁止客户端设置自己的窗口位置**。而贴图的本质就是「把一个浮窗放在屏幕的精确坐标上」——这件事在 Wayland 原生下做不到。

替代协议 `wlr-layer-shell` 可以做置顶浮层，但有两个硬伤：
1. **只能锚定到屏幕边缘或角落，不支持任意坐标定位** —— 贴图需要的正是任意坐标
2. **GNOME / mutter 完全不支持该协议**（KDE Plasma 支持）—— 而 GNOME 是 Linux 桌面占比最大的环境

叠加问题：全局快捷键在 Wayland 上同样没有着落。我们选型里的 `global-hotkey` crate，其 [Wayland support #162](https://github.com/tauri-apps/global-hotkey/issues/162) **至今仍是 open 状态**。

**唯一可行的绕法是走 XWayland**：把应用作为 X11 客户端运行，借 XWayland 拿回 X11 的窗口定位语义（Snipaste 的 Linux 版大概率就是这么做的）。但代价明确：
- HiDPI / 分数缩放下会模糊
- XWayland 客户端**看不到原生 Wayland 窗口**，窗口捕获会出问题

**结论：MVP 阶段 Linux 降级为「尽力而为」，不做承诺。** 主攻 Windows + macOS。README 里「三平台行为一致」的表述必须改掉，否则是对用户的虚假承诺。

### R2. macOS 的签名公证是真实成本

未签名公证的 app，用户下载后会被 Gatekeeper 拦下，得手动 `xattr -d com.apple.quarantine` 才能跑。对一款面向普通用户的工具，这个流失率是致命的。

签名需要 Apple Developer 账号，**$99/年，且必须由个人/公司实名承担**。开源项目没法回避这笔钱。需要提前决定谁出、怎么持续。

## 二、严重级：会决定 MVP 能否按期交付

### R3. 用 egui 做矢量标注编辑器，是逆着它的设计走

上一版技术选型推荐了 egui，这里要打个补丁。

egui 是 **immediate mode**（立即模式）：它天然不持有 UI 对象，每帧重绘。而标注编辑器需要的是**可选中、可拖拽、可改属性、可撤销重做的持久化矢量对象**（箭头、文本框、序号标记）。这意味着你得自己实现一整套 retained scene graph + 命中测试 + 变换矩阵 + undo 栈，再每帧重绘出来。

**能做，但工作量在选型时被明显低估了。** 这是 MVP 里最可能超期的模块。

> **一个好消息**：原本担心的 egui 中文 IME 输入问题，上游近期已密集修复（#7914 / #7898 CJK IME 支持、#4436 IME for chinese 均已合并，0.36.1 于 2026-08-07 发布）。中文标注输入不再是阻塞项，但仍需在原型阶段实测确认。

### R4. 多显示器 + 混合 DPI 是经典 bug 温床

- Windows 需要 per-monitor DPI awareness v2。用户常见 125% + 150% 混插，全屏遮罩要横跨所有屏、且每块屏用不同缩放渲染
- macOS 有 Retina 与非 Retina 混插
- **贴图窗口跨屏拖动时 DPI 会变**，必须重新采样，否则一拖到副屏就糊

坐标系换算（物理像素 / 逻辑像素 / 全局坐标）是这类工具最高发的 bug 来源。

### R5. macOS 上浮窗的层级与全屏 Space

贴图窗口要盖在全屏应用之上，需要正确设置 `NSWindow.level` 与 `collectionBehavior`（`.canJoinAllSpaces` + `.fullScreenAuxiliary`）。层级设太低盖不住，设太高会压住系统 UI。这块行为在不同 macOS 版本上有差异，只能靠实测。

## 三、范围级：MVP 必须砍掉的

| 功能 | 为什么砍 |
|---|---|
| **滚动长截图** | 实为「模拟滚动 + 逐帧捕获 + 特征匹配拼接」。跨应用兼容性极差（惯性滚动、sticky header 重复、各 App 滚动行为不一）。Snagit 做了几十年才做好，不是 MVP 该碰的 |
| **工作流可视化编排** | MVP 只需「截图自动进剪贴板 + 一个可配的 S3 兼容上传目标」。编排引擎是 v2 的事 |
| **OCR** | 要拖进 ONNX 运行时和模型文件，与「常驻内存小」的目标直接冲突。按需加载方案得单独设计 |
| **录屏 / GIF** | 硬件编码器三平台各一套，独立工作量级别 |
| **插件 API** | 接口一旦公开就难改。核心稳定前不要定 API |
| **历史库全文检索** | MVP 存本地文件 + 简单列表即可 |

## 四、战略级：非技术风险

### R6. 贴图本身不是护城河

贴图功能的最小实现两周就能做出来。**Snipaste 的护城河不是「有贴图」，是十年打磨出的手感**——缩放的阻尼、透明度调节、贴图分组、鼠标穿透、图像对比模式、整套快捷键肌肉记忆。

做到 80% 很快，做到能让老用户迁移很慢。要有心理准备：第一版一定不如 Snipaste 好用。

### R7. 「商用免费」对个人用户价值为零

这是目前定位里最大的逻辑漏洞。Snipaste **个人使用本来就免费**。所以「商用免费」这个差异点，对个人开发者完全没有吸引力，只对公司/团队采购有效。

**必须先想清楚 MVP 的目标用户是谁**：
- 如果是个人开发者 → 差异点只能是「开源可改」+「工作流自动化」，不是价格
- 如果是企业/团队 → 那 MVP 该优先做的是自建上传目标、批量部署、合规审计，而不是打磨贴图手感

这个问题不回答，MVP 的功能优先级就没有依据。

### R8. 单人维护三平台开源桌面工具的负担

Snipaste 是全职在做。三平台的 issue 队列会迅速被平台特定 bug 淹没——尤其是各种 Linux 发行版和显卡驱动组合。R1 的 Linux 降级决策，同时也是控制维护负担的决策。

### R9. Rust 桌面 GUI 生态仍在演进

egui / iced / slint 都还在快速迭代，API 会变。会有相当比例的时间花在跟 GUI 框架搏斗上，而非产品本身。这是选择 Rust 原生路线的真实代价（换来的是内存与延迟指标）。

## 五、建议的 MVP 范围

**平台**：Windows + macOS。Linux 标注为实验性，仅保证 X11 / XWayland 下可用。

**功能**：
- 区域 / 窗口 / 全屏捕获，多显示器支持
- 截图自动进剪贴板
- **贴图**：置顶浮窗、缩放、透明度调节、鼠标穿透、关闭
- 基础标注：矩形、箭头、文字、马赛克
- 全局快捷键

**不做**：滚动截图、OCR、录屏、工作流编排、插件 API、云同步、历史库检索。

## 六、写产品代码之前，先做三个原型验证

不要直接开工，先用三个一次性 demo 把最大的不确定性打掉：

1. **贴图窗口的置顶行为**（约 2–3 天）——重点验证 macOS 全屏 Space 上的层级表现，以及 Windows 多显示器混合 DPI 下的跨屏拖动。**这是产品的立身之本，必须第一个验证。**
2. **egui 的矢量标注对象编辑 + 中文 IME 输入**（约 3–5 天）——如果 egui 撑不住，趁早换 Slint，越晚代价越大。
3. **热路径延迟实测**（约 1–2 天）——快捷键 → 遮罩首帧是否能进 50ms。达不到就得重新审视 GUI 方案。

三个原型都通过，再开始写正式代码。

# 附：原型 1 实测结论

> 2026-09-03。代码见 [`prototypes/pin-window`](../prototypes/pin-window/)。
> 实测环境：macOS 26.5.1、Rust 1.97-nightly、winit 0.30.13、softbuffer 0.4.8、objc2-app-kit 0.3.2。
> **单显示器（2940×1912 @ scale 2）**。

## 已验证通过

**1. Rust 路线可行，无需自己写 FFI。**
经 `winit` 取 `RawWindowHandle::AppKit` → `NSView::window()` 可直达 `NSWindow`，
`setLevel` / `setCollectionBehavior` / `setAlphaValue` / `setIgnoresMouseEvents` 全部可用，
且在 objc2-app-kit 0.3.2 中**已是 safe API**，无需 unsafe 块。这消除了「Rust 做贴图要写大量 FFI」的顾虑。

**2. 无边框浮窗渲染正确。** 窗口无任何系统装饰，边框完整，可按任意物理坐标定位。

**3. 按物理像素渲染，不糊。** 测试图案中 1 物理像素宽的交替细线在 2x 屏上根根分明，
未被系统缩放模糊 —— 说明 winit + softbuffer 的渲染走的是物理像素路径，符合贴图对清晰度的要求。

## 发现的问题

**4. 启动时会收到一次「假的」DPI 变化事件。**
实测在窗口创建后立刻收到 `ScaleFactorChanged { 2 -> 2 }`，前后值完全相同。
产品代码若直接在该事件里触发贴图重采样，会造成无谓的重绘。
**结论：必须对 scale factor 做前后值比对去重，不能无条件响应该事件。**

## 未能验证（需补做）

**5. 全屏应用之上的浮窗行为 —— 已解决。**

经四轮排查定位到根因并找到可行方案。

### 排查过程

| 轮次 | 变量 | 结果 |
|---|---|---|
| 1a | winit NSWindow，level=Status(25)，cb=CanJoinAllSpaces\|FullScreenAuxiliary\|Stationary | 失败 |
| 1b | 追加 level=101/1000/2³¹−17，追加 `Accessory` 激活策略，共 8 组 | 全部失败 |
| 1b′ | 补上遗漏的 `orderFrontRegardless()`，加入 `isVisible`/`isOnActiveSpace` 探针 | 仍失败 |
| 1b″ | 改用 `FullScreenNone`（cb=593）、`仅CanJoinAllSpaces`（cb=17），并打成 .app bundle 固化 `LSUIElement=1` | 仍失败 |
| **1c** | **改用 `NSPanel` + `NonactivatingPanel` styleMask**，其余参数与失败轮次完全一致 | **通过** |

### 沿途排除的假设

- **不是层级问题**：25 / 101 / 1000 / 2³¹−17 均正确写入并可读回，全部失败。
- **不是 winit 覆盖了设置**：`collectionBehavior` 读回值（337 / 593 / 17）与设置完全一致。
- **不是漏调 `orderFrontRegardless`**：补上后仍失败。
- **不是激活策略**：运行时 `setActivationPolicy` 与 bundle 内 `LSUIElement=1` 两种方式均无效。
- **不是 `FullScreenAuxiliary` 用错**：换成 `FullScreenNone` 及去掉全屏标志位，同样失败。

关键诊断信号来自探针：全屏期间恒为 `isVisible=true` 且 `isOnActiveSpace=false` ——
窗口活着，但从未进入全屏 Space。这把病因从「层级不够高」精确切换到了「Space 归属」。

### 结论

> **`NSWindow` 无论如何配置都无法进入他人全屏应用的 Space；
> 必须使用 `NSPanel` 且 styleMask 含 `NonactivatingPanel`。**

实测数据：NSPanel 方案连续 197 次采样，`isOnActiveSpace` 全程为 `true`，零次 `false`，
覆盖全屏期间未中断。这是 Raycast / Alfred / CleanShot X 一类覆盖层工具的通行结构。

**这不是 macOS 的系统限制，而是 winit 的窗口类型限制。** 代码见 `prototypes/pin-panel`。

### 对架构的影响（已同步至技术选型）

macOS 上贴图窗口与捕获遮罩**都不能用 winit 创建**（后者同样需要覆盖全屏应用才能截到图）。
两者均须自行用 objc2 创建 NSPanel，再把 `CAMetalLayer` 挂到其 contentView 上供 wgpu 渲染。
winit 在 macOS 上的作用因此大幅缩小，跨平台窗口抽象需要自己写。

**6. 多显示器混合 DPI —— 未验证。** 测试机仅一块显示器，无法构造跨屏 DPI 变化场景。
**此项需在双屏且两屏缩放不同的环境下补测。**

**7. Windows 侧全部未验证。** 已给出 `WS_EX_LAYERED` / `WS_EX_TRANSPARENT` / `HWND_TOPMOST`
的对照实现，但测试机为 macOS，代码未经编译与运行验证。

## 当前判断

原型 1 的核心目标已达成：**R5 已从「最大未知风险」降级为「已知且有解的实现约束」。**

代价是技术选型需要修订 —— macOS 上不能依赖 winit 建窗，跨平台窗口层要自己写（见技术选型文档）。
这增加了工作量，但路径是明确的，不再有方向性的不确定。

仍未验证：多显示器混合 DPI（R4，缺硬件）、Windows 侧全部行为。

# 附：原型 2 实测结论

> 2026-09-03。代码见 [`prototypes/annot-editor`](../prototypes/annot-editor/)。
> egui / eframe 0.36.1，macOS 26.5.1。

## R3 的结论：可行，且工作量小于此前估计

原风险条目称「用 egui 做矢量标注编辑器是逆着它的设计走……工作量在选型时被明显低估」。
实测后**该判断偏保守**：

**396 行**（不含注释与空行）即实现了完整可用的标注编辑器，包含：
三种图元（矩形 / 箭头 / 文字）、命中测试（含点到线段距离）、点选、拖动、
拖角缩放、删除、快照式撤销重做栈、颜色与粗细调节。

**帧耗时 0.30–0.52ms**，远低于预算。immediate mode 需要自建 retained scene graph
与命中测试是事实，但这部分代码量有限、逻辑直白，不构成选型层面的障碍。

**结论：egui 保留为标注编辑器方案，不必换 Slint。**

## 发现的问题

**1. egui 不含任何 CJK 字形，必须手动加载字体。**
不加载的话界面中文全为豆腐块。产品需决定：内嵌字体（增加包体积）或依赖系统字体
（各平台路径不同，需维护候选列表）。原型采用后者，候选路径见 `install_cjk_font()`。

**2. 单字体替换不够，需要 fallback 链。**
原型将 STHeiti 插入 Proportional 家族首位后，工具栏上的 `⇧` 符号变成豆腐块 ——
该字体不含此字形。**产品必须实现多字体 fallback，不能简单替换首选字体。**

**3. 原位文字编辑需要三处补偿，否则文字会在编辑态与非编辑态之间跳动。**
实测暴露的位置偏移，根因有三：
- `ui.put()` 内部使用 `centered_and_justified` 布局，会将文字居中，
  而非编辑态的 `painter.text()` 用的是 `Align2::LEFT_TOP`；
  须改用 `UiBuilder + Layout::left_to_right(Align::Min)`
- `TextEdit` 默认 `margin` 为 `Margin::symmetric(4, 2)`，须清零
- `TextEdit` 默认带 `Frame`（白底 + 边框），须设为 `Frame::NONE`

这三点均非显然，是 egui 做所见即所得标注的实际成本，需计入排期。

**4. egui 0.36 的 API 变动是真实成本（R9 的具体证据）。**
`eframe::App` 的入口由 `update(&egui::Context)` 改为 `ui(&mut egui::Ui)`；
`TopBottomPanel` 已被移除；`TextEdit::frame()` 由收 `bool` 改为收 `Frame`。
按既有印象编写的代码全部编译失败，须翻阅源码确认签名。
**升级 egui 版本将是持续的维护成本，需纳入长期预算。**

## 已验证通过

- 中文 IME 输入可用：拼音上屏正常，文字正确进入文本框（实测输入「你好萨基弗萨发的」）
- 撤销 / 重做栈工作正常
- 选中态手柄、拖动、缩放交互正常

## 复测结果：全部通过

修复三处位置补偿后复测，**中文输入链路完整可用**：

- **文字位置对齐** —— 编辑态与非编辑态之间不再跳动
- **候选词窗跟随光标** —— 候选列表紧贴预编辑文本下方弹出，
  未出现 egui 历史上「候选窗飘到屏幕角落」的问题
- **预编辑文本原位渲染** —— 带下划线的拼音正确显示在文本对象位置，而非别处
- **拼音态退格正常** —— 删除拼音字母，不误删已上屏汉字

**R3 关闭。egui 作为标注编辑器方案确认可行，无需换 Slint。**

## 附带修复

文字工具每次点击都会落一个空文本对象，误点会在画布上堆积不可见的空对象。
已改为编辑结束时若内容为空则自动丢弃 —— 这是产品必需的行为，非框架限制。

# 附：原型 3 实测结论 —— 热路径延迟

> 2026-09-03。代码见 [`prototypes/hotpath`](../prototypes/hotpath/)。
> macOS 26.5.1，主屏 1470×956 @2x。遮罩使用 NSPanel（沿用原型 1 结论）。
> 计时起点为**热键回调触发**，不含系统从物理按键到回调的事件派发耗时。

## 指标达标，余量约两个数量级

36 轮 × 每轮 12 次采样：

| 路径 | 中位 | 最大（各轮中位的最大值） |
|---|---|---|
| **预热**（面板预建，仅排入+绘制） | **0.11ms** | 0.25ms |
| 冷建（每次现建 NSPanel） | 0.96ms | 2.60ms |

目标为 < 50ms、理想 < 16ms（一帧）。**实测 0.11ms，达标且余量极大。**
即便走冷建路径也只有 0.96ms，同样远在预算内。

## 修订技术选型中的一条断言

原文称：「遮罩窗口预创建但不显示 —— 付出几 MB 的常驻代价，换取唤起时省掉窗口创建开销，
**这是唯一值得的预热**」。

实测数据不支持该说法：**预热相对冷建仅省下 0.86ms（中位）**。
在 50ms 的预算下，这点收益可以忽略，却要为此常驻一个全屏面板的内存，
与「常驻内存 < 30MB」的目标直接冲突。

**结论：遮罩改为按需创建，取消预热。** 省下的内存比省下的 0.86ms 有价值得多。

## 一次被推翻的归因（记录以免重犯）

首版基准中，预热路径的中位耗时随轮次**单调劣化 27 倍**（0.29ms → 7.95ms），
而冷建路径保持平稳。当时归因为「冷路径只调 `orderOut()` 未调 `close()`，
泄漏的面板堆积在 NSApp 窗口列表中，拖慢了窗口排序」。

**该归因是错的。** 修正版加入 `close()` 与 `autoreleasepool` 后复测：

- 劣化完全消失（前半程中位 0.11ms vs 后半程 0.10ms，36 轮无趋势）
- **但窗口列表仍以每轮 +12 的速度线性增长，最终达 433** ——
  说明 `close()` 并未将窗口移出 `NSApp.windows()`

即：**窗口积累到 433 个也未造成任何劣化**，窗口列表长度不是病因。
真正起作用的是补上的 `autoreleasepool` —— 首版在单次热键回调内跑 24 次
Cocoa 调用且从不返回 run loop，自动释放对象持续堆积在外层池中，这才是劣化根源。

**对产品的意义有限**：真实应用每次交互都会回到 run loop，系统自动排空自动释放池，
不会出现该情形。这更多是编写基准测试时的陷阱，而非产品风险。
记录于此仅为提醒：**在不返回 run loop 的密集 Cocoa 调用循环中，必须手动加 autorelease pool。**

# 附：原型 4 实测结论 —— 多显示器（R4）

> 2026-09-03。代码见 [`prototypes/multiscreen`](../prototypes/multiscreen/)。
> 实测环境：内置 Retina（frame `(0,0) 1470×956`，scale 2）
> + DELL U2518D（frame `(-1920,-124) 1920×1080`，scale 2）。

## 关键发现：单个窗口无法覆盖多块显示器

原设计隐含假设「一个全屏遮罩窗口覆盖整个桌面」。**该假设不成立。**

实测：按所有屏的并集构造一个 NSPanel（原点 `(-1920,-124)`，尺寸 `3390×1080`，
几何上完全包住两块屏），结果**只有 DELL 被覆盖，内置屏毫无变化**。

原因是 macOS 的「**显示器各自拥有独立空间**」（Displays have separate Spaces）
为系统默认（`com.apple.spaces spans-displays` 未设置即为开启独立空间）。
每块屏是独立 Space，而一个窗口只能属于一个 Space，因此无法跨屏铺开。

**解决方案已验证：每块屏各建一个遮罩面板。** 实测两块屏均被正确覆盖，
各面板 `screen()` 正确报告其所属显示器。

### 对架构的影响

捕获遮罩**不是一个窗口，而是 N 个窗口**（每屏一个）。由此带来的复杂度：

- N 个面板的创建、显示、隐藏、销毁需统一管理生命周期
- **跨屏框选**：用户可能从一块屏拖到另一块，选区状态须在多个遮罩窗口间协调，
  鼠标事件要跨窗口串起来 —— 这比单窗口内的框选复杂得多
- 显示器热插拔时需要动态增删遮罩
- 最终截图需按各屏的 scale 分别取像素再拼接

这项复杂度在原设计中完全没有体现，需计入排期。

## 次要发现：全局坐标系包含负坐标

外接屏 frame 原点为 `(-1920, -124)`。macOS 全局坐标系原点在**主屏左下角**，
副屏可位于负坐标区。**任何「从 (0,0) 起算」的假设都会在多屏下出错**，
包括遮罩定位、选区坐标换算、贴图窗口落位。

实测面板以负坐标 `(-1140, 306)` 定位到外接屏中央，工作正常 —— 负坐标本身可用，
只要代码不做错误假设。

## 已验证通过

- 两块显示器均被正确枚举，`frame` / `backingScaleFactor` / `localizedName` 均可读
- 面板可按负坐标精确定位到副屏
- 面板 `screen()` 正确报告所属显示器，跨屏后 `backingScaleFactor` 一致

## 仍未验证：混合 DPI

**当前两块屏 `backingScaleFactor` 均为 2，不构成混合 DPI 场景。**
要验证需将某块屏切到非 HiDPI 模式（系统设置 → 显示器 → 选择一个非「Retina」分辨率），
使其 scale 变为 1，再复测跨屏拖动时的 `ScaleFactorChanged` 与重采样清晰度。

R4 因此**部分关闭**：多屏坐标与跨屏覆盖已解决，混合 DPI 待补测。
