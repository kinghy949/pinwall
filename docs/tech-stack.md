# 技术选型

> 硬性约束：**常驻内存小、截图响应快、跨三平台**。
> 本文档的性能数字为量级估算（依据同类项目公开表现），不是实测结果，待有原型后以实测替换。

## 一、核心判断：把应用拆成冷热两条路径

截图工具和普通桌面应用有个本质区别 —— 它**长期常驻托盘，但绝大多数时间不工作**。因此性能要求是分裂的：

| 路径 | 场景 | 硬指标 |
|---|---|---|
| **热路径** | 按下快捷键 → 全屏选区遮罩出现 | 延迟 < 50ms，理想 < 16ms（一帧） |
| **温路径** | 选区完成 → 标注编辑器 | 延迟 < 150ms，用户可感知但可接受 |
| **冷路径** | 设置界面、历史库、工作流配置 | 延迟 < 500ms 均可 |
| **常驻态** | 99% 的时间：什么都不干 | 内存 < 30MB，CPU ≈ 0% |

**结论：热路径决定选型。** 一个每次唤起要等 300ms 才出遮罩的截图工具，功能再多也是失败的。

## 二、方案对比

| 方案 | 常驻内存（量级） | 安装包 | 热路径延迟 | 判断 |
|---|---|---|---|---|
| Electron | 150–250 MB | 80–150 MB | 差（Chromium 全家桶常驻） | ❌ 直接出局 |
| Flutter | 60–120 MB | 20–40 MB | 中等 | ❌ 深度系统集成吃力 |
| Tauri v2（WebView） | 60–120 MB | 8–15 MB | 中等偏差（见下） | ⚠️ 不适合热路径 |
| **Rust + wgpu 原生** | **20–40 MB** | **10–20 MB** | **优** | ✅ **推荐** |
| Qt / C++ | 30–60 MB | 20–40 MB | 优 | 可行，但开发效率与生态不如 Rust |

### 为什么否掉 Tauri

Tauri 的包体积确实很小，这点常被拿来当卖点，但它省的是**磁盘**，不是**内存和延迟**：

1. **WebView 进程本身就要 60–100MB 常驻**。系统 WebView（WebView2 / WKWebView）是独立进程树，一个理应 20MB 的托盘工具会变成 100MB+。
2. **WebView 冷启动有几百毫秒**。可以靠预热隐藏窗口规避，但预热就等于常驻内存一直付着 —— 省不掉。
3. **全屏透明遮罩是 WebView 的弱项**。多显示器 + 混合 DPI + 透明穿透合成，在三个平台上的 WebView 行为各不相同，正是最容易出诡异 bug 的地方。

Tauri 适合"用户主动打开、用完关掉"的应用。**Snapzen 恰好相反**，所以不合适。

## 三、推荐技术栈

### 核心

- **语言：Rust** —— 无 GC 意味着没有 STW 停顿，热路径延迟可预测；内存占用可控；跨平台 FFI 生态成熟。

### GUI

- **`egui` + `wgpu`** —— 立即模式 GUI，GPU 渲染，依赖极少，编译产物小，帧延迟低且稳定。选区遮罩本质上就是「一个十字光标 + 一个矩形 + 一排工具按钮」，这正是 egui 的最佳场景。
- 备选 **`slint`**：声明式，视觉打磨上限更高（对标 CleanShot X 的精致度时更有余地），同样为低资源场景设计。
- **建议策略**：热路径（选区遮罩）用 egui 保证延迟；如果后期发现标注编辑器/设置界面的视觉打磨受限于 egui，**只把冷路径换成 Slint**，热路径不动。

### 屏幕捕获（各平台走原生 API，不要图省事用跨平台封装）

| 平台 | API | Rust crate |
|---|---|---|
| Windows | Windows.Graphics.Capture / Desktop Duplication | `windows-rs` |
| macOS | ScreenCaptureKit | `objc2` + `objc2-screen-capture-kit` |
| Linux | PipeWire（Wayland）/ XCB（X11） | `pipewire-rs`, `x11rb` |

跨平台捕获库（如 `screenshots`）适合做早期原型，但滚动截图、多显示器 HiDPI、Wayland 权限这些坑最终都得下沉到原生 API。

### 其他关键依赖

| 用途 | 选型 | 说明 |
|---|---|---|
| 全局快捷键 | `global-hotkey` | 跨三平台 |
| 托盘 | `tray-icon` | 与上者同作者，配套好 |
| 窗口 | `winit` | egui/wgpu 的标准搭配 |
| 图像处理 | `image` + `fast_image_resize` | 后者用 SIMD，缩放快一个数量级 |
| PNG 编码 | `zune-png` / `oxipng` | 比默认编码器快，且压缩率更好 |
| 异步运行时 | `tokio`（仅上传/OCR 用） | **不要**让它进热路径 |
| OCR | ONNX Runtime + PaddleOCR | 中文识别优于 Tesseract；按需加载，不常驻 |
| 录屏编码 | 硬件编码器（NVENC / VideoToolbox / VAAPI） | 软编码 CPU 占用不可接受 |
| 配置 | TOML + `serde` | 纯文本，用户可手改，便于同步 |

## 四、为达成性能指标的架构约束

1. **常驻进程做到最小**：托盘进程只保留快捷键监听 + 托盘图标 + 配置，目标常驻 < 15MB。GPU 上下文、编辑器、OCR 模型全部按需加载。
2. **热路径零分配、零 IO**：快捷键按下到遮罩显示之间，不读磁盘、不解析配置、不初始化子系统。所有需要的状态在启动时就备好。
3. **遮罩窗口预创建但不显示**：付出几 MB 的常驻代价，换取唤起时省掉窗口创建开销 —— 这是唯一值得的预热。
4. **捕获与编码分离**：先把帧交给用户看到（遮罩已可交互），编码压缩放到后台线程。
5. **OCR / 上传 / 录屏编码全部离开主线程**，主线程只负责渲染。
6. **建立性能回归测试**：把「快捷键 → 遮罩首帧」的延迟和常驻内存做成 CI 指标，超阈值就挂。性能是设计出来的，也是守出来的 —— 没有基线，三个月后必然劣化。

## 五、待验证的风险

- **Wayland 下的全局快捷键与全屏遮罩**：权限模型限制多，是三平台里最不确定的一环，建议尽早做原型验证。
- **macOS 屏幕录制权限**：首次使用需用户授权并重启应用，交互流程要提前设计。
- **egui 的视觉上限**：标注编辑器能否做到 CleanShot X 级别的精致度，需要出原型后评估，否则按上文策略换 Slint。
